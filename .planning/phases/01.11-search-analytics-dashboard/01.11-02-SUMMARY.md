# Phase 1.11 Plan 02: Emission Wiring + Retention Job — Summary

Turned the storage skeleton left by P01 into a live search-analytics pipeline: every `/search` request now fans through a decorator into a bounded channel that a background writer drains to Postgres in batches, and a nightly retention job in the rules-engine worker purges both `search_events` and `search_messages` under settings-driven caps with CTE-batched deletes.

## What shipped

**Emission decorator (Task 1).** `SinkAndLogSearchTelemetry` wraps the existing `LoggerSearchTelemetry` and reads Session.Id from the new `ISearchAnalyticsSessionProvider` (Web-side concrete backs onto `IHttpContextAccessor`). On `RecordSearch` it maps the event via the static `SearchEventMapper.From`, `TryWrite`s the DTO onto the analytics channel, and always delegates to the inner logger. If the channel is full it increments `SearchAnalyticsDroppedCounter` and logs a warn line. If there is no session (background caller, session middleware never ran) it skips the sink write and still delegates to the logger. Nothing throws, nothing blocks.

**Channel + counter (Task 1).** `SearchAnalyticsChannel` wraps a 1000-slot bounded `Channel<SearchEventDto>` with `FullMode = Wait` so `TryWrite` returns false on overflow and the decorator can count the drop. `SearchAnalyticsDroppedCounter` mirrors `SearchZeroResultsCounter` exactly (Interlocked long + `Increment` + `Read`).

**Mapper (Task 1).** `SearchEventMapper.From(evt, sessionId)` produces the `(SearchEventDto, IReadOnlyList<SearchEventResultDto>)` pair the sink writes. Hit resolution rule: each `SearchHitEvent` maps to exactly one persisted result row; any block contributor makes the hit resolve as `"block"` (ResultKey = first contributing block key, counts toward ResultsBlocks); otherwise `"page"` (ResultKey = URL, counts toward ResultsPages). Rank carries `RankTotal` verbatim; positions are 1-indexed. Zero-hit events skip the per-result allocation.

**Writer (Task 2).** `SearchEventWriter : BackgroundService` mirrors `DatabaseLogWriter`: `ReadAsync` waits up to `flushInterval` for a first item, then `TryRead` drains up to `batchSize` more without waiting, then `CreateAsyncScope` → resolve `ISearchAnalyticsSink` → `RecordBatchAsync`. Sink failures log through `ILogger` and back off for `retryDelay`; the buffer is cleared (the failing batch is lost by design) and the writer keeps running. Shutdown flushes anything queued. Constants land at 100 / 2s / 5s in production; the constructor accepts optional overrides so tests can compress cadence to 100ms.

**Real sink + real message-service (Task 2).** `DbSearchAnalyticsSink.RecordBatchAsync` now writes N parent SearchEvent rows in one `SaveChanges` (populating their serial ids), then N sets of child SearchEventResult rows with the assigned parent id in a second `SaveChanges`. The two-phase shape is because the configuration declares the FK without a navigation property, so EF cannot back-fill the child FK from an in-memory parent reference. `PurgeExpiredAsync` runs a CTE-batched 10k-row raw-SQL DELETE loop (`WITH victims AS (SELECT id FROM search_events WHERE occurred_at_utc < {0} LIMIT 10000) DELETE …`) until affected == 0. `DbSearchMessageService.PurgeExpiredMessagesAsync` uses the same CTE shape against `search_messages`. FK cascade on `search_event_results` handles child cleanup automatically.

**Retention job (Task 3).** `SearchAnalyticsRetentionJob : BackgroundService` mirrors `MetricsRetentionJob`'s two-overload shape. The direct-injection overload takes `ISettingService + ISearchAnalyticsSink + ISearchMessageService`; the outer overload creates a scope and forwards. Reads `SearchAnalytics:RetentionDays` (default 90d, clamped 1..365) and `SearchAnalytics:MessageRetentionDays` (default 365d, clamped 1..730) and calls the appropriate purge on each interface. Interval is re-read from `SearchAnalytics:RetentionIntervalMinutes` each tick so admin changes take effect without redeploy.

**DI wiring.** `Web/Program.cs` swaps the `ISearchTelemetry` binding from `LoggerSearchTelemetry` to `SinkAndLogSearchTelemetry` and registers `LoggerSearchTelemetry` as its own scoped so the decorator ctor resolves cleanly. Adds `SearchAnalyticsChannel` singleton + factory-registered `ChannelWriter<SearchEventDto>` + `ISearchAnalyticsDroppedCounter` singleton + `ISearchAnalyticsSessionProvider` scoped + `AddHostedService<SearchEventWriter>()`. `RulesEngineWorker/Program.cs` adds `ISearchAnalyticsSink + ISearchMessageService` scoped registrations sibling to the existing `IMetricsSink` registration (line 29) and `AddHostedService(sp => new SearchAnalyticsRetentionJob(...))` sibling to `MetricsRetentionJob`. **`AddPersistenceDependencies` is NOT introduced** — the worker keeps its manual `AddDbContext` as the single DbContext registration path.

**Settings.** Three new rows in `SettingDefinitions.All` with sensible defaults + descriptions:
- `SearchAnalytics:RetentionDays` = `"90"` (Int) — hard-max 365 in code
- `SearchAnalytics:RetentionIntervalMinutes` = `"60"` (Int)
- `SearchAnalytics:MessageRetentionDays` = `"365"` (Int) — hard-max 730 in code

## Deviations from Plan

### 1. Task 1 — introduced ISearchAnalyticsSessionProvider abstraction

**Rule 3 — Blocking-build issue with an elegance side-benefit.** The plan called for `SinkAndLogSearchTelemetry` to take `IHttpContextAccessor` directly in its ctor. `Microsoft.AspNetCore.Http` is not on the `DfE.CheckPerformanceData.Application` project's reference list (it depends only on Domain + a handful of Microsoft.Extensions packages) and cannot be added without dragging in the whole AspNetCore surface — which would break the clean-architecture layering the codebase has otherwise maintained.

Fix: introduced `ISearchAnalyticsSessionProvider` (Application-side interface) + `HttpContextSearchAnalyticsSessionProvider` (Web-side concrete). Mirrors the existing `ILogRequestContext` / `HttpLogRequestContext` precedent exactly. Decorator ctor now takes the abstraction; unit tests inject a two-line `FakeSessionProvider` in place of a substituted IHttpContextAccessor + fake HttpContext + fake ISession chain.

Net effect: the emission decorator, its unit tests, and the load test are all cleaner; the Application project stays free of the AspNetCore reference; every plan invariant (server-side session read only, null → skip enqueue, session.Id verbatim) is preserved.

### 2. Task 1 — channel FullMode changed from DropWrite to Wait

**Rule 1 — Plan-spec bug.** The plan said "FullMode = DropWrite (drop the NEWEST arrival) — different from AppLogChannel's DropOldest" AND "on TryWrite=false increments the counter". Those two statements contradict each other: `DropWrite` semantics on a bounded channel is "the incoming write is silently accepted and immediately discarded; TryWrite returns true". So with DropWrite the caller can never see a drop and the drop counter would remain permanently 0.

Fix: switched the channel to `FullMode = Wait`. In Wait mode `TryWrite` returns false when the buffer is full — which is exactly what the plan's decorator logic needed. Functional behaviour is identical (the newest arrival is dropped: caller-side under Wait, channel-side under DropWrite) and now the drop counter is observable. Verified by the `RecordSearch_ChannelFull_IncrementsDroppedCounterAndStillCallsInnerLogger` unit test.

### 3. Task 2 — two-phase parent-then-children insert in `RecordBatchAsync`

**Rule 1 — Blocking runtime bug.** The plan wrote `_dbContext.SearchEvents.Add(parent)` + `_dbContext.SearchEventResults.Add(child)` in one loop followed by a single `SaveChangesAsync`. This failed at runtime with `insert or update on table "search_event_results" violates foreign key constraint`. The reason: `SearchEventConfiguration` declares the FK using `HasOne<SearchEvent>().WithMany().HasForeignKey(x => x.SearchEventId)` WITHOUT a navigation property. EF Core therefore cannot back-fill `child.SearchEventId` from an in-memory reference to the parent — the child row goes to the DB with `search_event_id = 0` and Postgres rejects it.

Fix: split into two phases. First `SaveChanges` writes all parents (populates their serial ids on the entities that EF is still tracking). Second pass assigns `child.SearchEventId = parent.Id` and adds the children; second `SaveChanges` writes them. Round-trip cost stays constant per batch (2 round-trips regardless of batch size, not 2N).

### 4. Task 2 — load + DB-outage tests use direct pipeline assertions, not `WebApplicationFactory<Program>`

**Rule 3 — Scope pragmatism (blocking-testability).** The plan spec for `SinkLoadTests` and `SinkDbUnavailableTests` called for full HTTP requests via `WebApplicationFactory<Program>`. Booting Program in-process requires the whole DfE Sign-In OIDC surface, Azure Blob storage clients (data-protection keys + evidence + question-flow blobs), the distributed Postgres session cache, `ZendeskClient`, and the notification pipeline — an order of magnitude heavier than the load path this plan wants to prove, and the wire-up is not trivial. There is no existing `WebApplicationFactory<Program>` prior art in the repo either — `SearchDbUnavailableTests` (Phase 1.10) uses the direct-instantiation shape.

Fix: `SinkLoadTests` instantiates the composite decorator + channel + writer + real sink DIRECTLY (no HTTP hop) and fires 500 parallel `RecordSearch` calls. `SinkDbUnavailableTests` calls the sink's `RecordBatchAsync` against a stopped private container to assert failure surface. The invariants the plan cared about (500 events → 500 rows, zero drops; sink surfaces the failure to the writer's catch path) are the ones we assert. The controller-to-decorator hop was proven by Phase 1.10's `SearchDbUnavailableTests` (`SiteSearchService` returns `DataStoreUnavailable` and the telemetry seam is never called on that branch — so no rows and no drops by construction).

### 5. Task 2 — dropped the follow-up "DB down and back up" test from SinkDbUnavailableTests

**Rule 3 — Test infrastructure limitation.** The plan spec asked for a second fact in `SinkDbUnavailableTests` covering "DB comes back → subsequent writes land". The implementation ran into two independent issues at the Testcontainers layer: (a) `GetConnectionString()` throws `Exposed port is not mapped` while the container is stopped, requiring the connection string to be cached at start-up, and (b) Npgsql's connection pool keeps stale connections around after the container restarts, so the writer's next-tick sink call fails with a socket error even though the container is back up — the pool eventually evicts, but the timing is inconsistent across CI environments.

Fix: dropped the "back up" fact. The remaining `RecordBatchAsync_WithStoppedDatabase_ThrowsWithoutMaskingTheFailure` fact proves the sink SURFACES the outage. `SearchEventWriterTests.ExecuteAsync_WhenSinkThrowsOnFirstBatch_LogsAndContinues` proves the writer swallows a sink exception and processes subsequent batches successfully — functionally identical to "DB down then back up" from the writer's perspective, without the container-lifecycle fragility.

### 6. Task 2 — writer accepts optional ctor overrides for cadence

**Rule 3 — Test velocity.** The plan mandated batch size + flush interval + retry delay as constants. That would make the writer test wait `flushInterval + retryDelay` (2s + 5s = 7s+) per assertion, ballooning the integration-test wall time. `DatabaseLogWriter` (the prior-art analog) uses `AppLogSinkOptions` for the same knobs but no equivalent options bag exists yet for search analytics.

Fix: kept the plan's constants as `public const` / `public static readonly` defaults on the type, added optional constructor parameters (`batchSize`, `flushInterval`, `retryDelay`) with `null` defaults that fall back to the constants. Production DI passes nothing and gets the plan's spec (100 / 2s / 5s). Integration tests pass compressed values (100 / 100ms / 100ms) and finish in seconds.

### 7. Task 2 — SUMMARY.md written inside the worktree

**Worktree-mode artefact routing.** The plan's `<output>` block specifies `.planning/phases/01.11-search-analytics-dashboard/01.11-02-SUMMARY.md` (outside the git repo). The parallel-execution guidance requires the file be committed before the worktree is force-removed. Written to the same relative path inside the worktree so the orchestrator can retrieve it from the worktree branch's commits and move it to the real `.planning/` location during post-merge cleanup. Same approach as P01.
