# Phase 1.11 Plan 05: SearchMessages Feedback Form — Summary

User-facing feedback path: a `Not the results you were expecting?` callout on `/search`, a GDS full-page form at `/Search/Feedback`, and a confirmation view showing the session ID the user can quote. Two load-bearing invariants — server-side session ID sourcing (spoofed form fields are ignored) and hide-my-email dropping the value before persist (persisted `email` column is literally NULL) — are locked in by integration tests against a real Postgres.

## What shipped

**Message-service write path (Task 1).** Extended `ISearchMessageService` (Analytics/ folder, no move) with `Task<long> CreateAsync(sessionId, whatLookingFor, whatGot, email, ct)`. Filled in `DbSearchMessageService.CreateAsync`: builds a `SearchMessage` entity with server-stamped `SubmittedAtUtc = DateTime.UtcNow` + `IsRead = false`, EF Add + SaveChanges, returns the auto-assigned id. Existing `PurgeExpiredMessagesAsync` untouched. P01 already registered the service scoped in `DependencyManager.cs`, so no DI edit here.

**Empty `SearchMessageSummaries.cs` stub.** Created at `Application/Analytics/SearchMessageSummaries.cs` as an empty namespace declaration so P06 has a stable file to extend with the inbox row / detail / paging shapes.

**Feedback controller (Task 2).** `SearchFeedbackController` at `[Route("/Search/Feedback")]`, `[AllowAnonymous]` (mirrors public `SearchController`). Three actions:

- `GET Index(ct)` — awaits `Session.LoadAsync(ct)`, captures `HttpContext.Session.Id`, calls `ISearchAnalyticsQueryService.GetLatestSearchForSessionAsync(sessionId, ct)`, builds a `SearchFeedbackViewModel { SessionId, PriorSearchPrefill }` where `PriorSearchPrefill` is either null or the formatted string `Search: "{queryRaw}" returned {N} results at {HH:mm} on {d MMM yyyy}` (InvariantCulture). Returns `View("~/Views/Search/Feedback.cshtml", model)`.
- `POST Submit(form, ct) [ValidateAntiForgeryToken]` — awaits `Session.LoadAsync(ct)`, re-reads `HttpContext.Session.Id` (IGNORES the posted view-model's SessionId). On invalid ModelState, constructs a fresh view-model (never assigns `form.SessionId = ...`) with server-owned session id + the user's re-posted values and re-renders. On valid ModelState, computes `email = form.HideMyEmail ? null : trim-or-null(form.Email)`, then calls `_messages.CreateAsync(sessionId, trimmed-what-looking-for, trim-or-null(what-got), email, ct)`. Stores the session id in `TempData["FeedbackSessionId"]` and redirects to Confirmation.
- `GET Confirmation` — reads the session id from TempData (with a fallback to current session), renders `~/Views/Search/FeedbackConfirmation.cshtml` so the user can copy their id.

**View-model shape.** `SearchFeedbackViewModel` carries `SessionId` (server → view display only, never trusted from POST), `PriorSearchPrefill` (server → view hint text), `WhatLookingFor [Required, StringLength(4000)]`, `WhatGot [StringLength(4000)]`, `Email [EmailAddress]`, `HideMyEmail bool`. All validation attributes fire under real model binding at POST time.

**Feedback.cshtml.** GDS full-page layout inside the standard `govuk-grid-row / govuk-grid-column-two-thirds` wrapper. Back-link + `<h1 class="govuk-heading-xl">Send us a note about a search</h1>` + intro paragraph. Error-summary rendered above the form when `ModelState` is invalid, listing each field's first error with `<a href="#{fieldName}">` links. The form:

1. **Session ID** — `<label>Your session ID</label>` + `<div class="govuk-hint">Quote this if you contact us again...</div>` + readonly `<input class="govuk-input" id="SessionIdDisplayOnly" name="SessionIdDisplayOnly" value="@Model.SessionId" readonly aria-describedby="session-id-hint" />`. NOT a hidden field — user-visible so they can copy it.
2. **What were you looking for?** — required `<textarea class="govuk-textarea" name="WhatLookingFor" rows="4">`, per-field error-message + `govuk-form-group--error` class when invalid.
3. **What did you actually get?** — optional `<textarea name="WhatGot" rows="4">` pre-filled from `Model.PriorSearchPrefill` (or the re-posted value on validation failure).
4. **Consent line** (verbatim, single Razor line): `If you provide your email address, it will be sent to the support team so they can reply to you.`
5. **Email address (optional)** — `<input type="email" name="Email" autocomplete="email">` with GDS email validation error rendering.
6. **Hide my email address from the support team** — GDS checkbox `<input type="checkbox" name="HideMyEmail" value="true">` with hint copy explaining the behaviour.
7. **Send** — `<button class="govuk-button" type="submit">`.

Antiforgery token emitted via `@Html.AntiForgeryToken()`.

**FeedbackConfirmation.cshtml.** `<h1>Thanks — we have received your note</h1>` + `<p>Your session ID is <strong>@Model.SessionId</strong>. If you contact us again, quote this ID so we can find your search history.</p>` + a link back to `/search`.

**Inset-text link on `Views/Search/Index.cshtml`.** One new block at the bottom of the shared `govuk-grid-column-two-thirds` wrapper, guarded on `!string.IsNullOrEmpty(Model.Query) && InvalidReason not DataStoreUnavailable and not BelowMinimumLength`. The single-block approach is DRY — one guard covers both the zero-result and results-present branches (both fall through to the block since they both satisfy the guard). The plan's acceptance criterion `grep -c "govuk-inset-text" == 1 or 2` is satisfied at 1.

## Deviations from Plan

### 1. HTTP-in-process TestServer + WebApplicationFactory swap → direct controller invocation + view-render (isMainPage:false)

**Rule 3 — Blocking test infra.** The plan's Task 2 `<action>` described the integration tests as `WebApplicationFactory + PostgresFixture`. I first tried a HostBuilder + TestServer + real controller + real session-middleware pipeline (matching SessionAbsoluteLifetimeMiddlewareTests exactly), which succeeded through model binding but crashed inside view rendering with `The layout view '_GovUkPageTemplate' could not be located`. Adding the GovUk RCL assembly as an `AddApplicationPart` fixed the layout lookup but then crashed inside layout-composition activating `EditableContentViewComponent` → `IContentBlockService` — the full public-facing layout dependency graph.

Fix: mirrored the exact split P03's Deviation 1 documented (SearchAnalyticsAuthTests / SearchAnalyticsControllerTests / SearchAnalyticsIndexViewRenderTests). Controller-scope tests invoke the action directly against a real Postgres DbContext with a FakeSession/FakeSessionFeature carrying a specified `Session.Id` — this exercises the ModelState.IsValid branch, the server-side session-id sourcing, the hide-my-email drop, the TempData carry to confirmation, and the DB persistence semantics. View-render tests use `ICompositeViewEngine.GetView(isMainPage:false)` to render `Feedback.cshtml` / `FeedbackConfirmation.cshtml` / `Search/Index.cshtml` standalone — no `_ViewStart`, no layout — and assert on markup. Net effect: identical coverage of the two invariants + form markup + inset-text markup without wiring the admin-content-block dep graph into the test host.

### 2. Antiforgery: production controller keeps `[ValidateAntiForgeryToken]`, tests don't validate the token

**Rule 3 — Test infra tradeoff.** Since the tests invoke `Submit` directly (not through the MVC filter pipeline), `[ValidateAntiForgeryToken]` is not in the code path they exercise. To lock the attribute presence, added a reflection-level assertion `Submit_HasValidateAntiForgeryTokenAttribute` that fails if a future refactor drops it. The `[AllowAnonymous]` gate on the controller is likewise reflection-tested.

### 3. Consent line laid out on a single Razor line

**Rule 2 — Correctness.** The verbatim consent copy from the spec (`If you provide your email address, it will be sent to the support team so they can reply to you.`) was initially written wrapped across three source lines for readability. Razor preserves the intervening whitespace + newlines, so the rendered HTML contained `will\n                sent` etc. and the `Assert.Contains(exact-string)` assertion failed. Fixed by putting the sentence on a single Razor line — the rendered HTML now carries the substring verbatim, matching the spec word-for-word. Other paragraphs remain wrapped for readability; only assertion-checked strings need this treatment.

### 4. On-validation-failure redisplay uses a fresh view-model, not `form.SessionId = ...`

**Rule 2 — Grep-clean invariant.** The plan's acceptance criteria include `grep -c "form.SessionId" src/…/SearchFeedbackController.cs == 0`. The initial GREEN pass had `form.SessionId = sessionId;` in the redisplay branch (a defensive server-side overwrite of any spoofed value) — semantically correct but grep-non-compliant. Refactored to construct a fresh `SearchFeedbackViewModel { SessionId = sessionId, WhatLookingFor = form.WhatLookingFor, ... }` on the redisplay branch instead, so `form.SessionId` never appears anywhere in the controller. Grep-clean invariant now holds; the user's typed inputs still round-trip on validation failure.

### 5. Inset-text link uses one guarded block, not one-per-branch

**Rule 2 — Elegance / SOLID.** The plan's acceptance says `grep -c "govuk-inset-text" == 2 (one per branch) OR 1 (single guarded block) — either is acceptable so long as the tests pass`. Chose the single-block approach: one `<div class="govuk-inset-text">` at the bottom of the `govuk-grid-column-two-thirds` wrapper, guarded on `!string.IsNullOrEmpty(Model.Query) && InvalidReason not DataStoreUnavailable and not BelowMinimumLength`. This is DRY — one guard covers both the zero-result and results-present branches. Both `ResultsPresent_RendersInsetTextLinkToFeedbackForm` and `ZeroResults_RendersInsetTextLinkToFeedbackForm` pass; `NoQueryPresent_OmitsInsetTextLink` proves the guard.

### 6. SUMMARY.md committed inside the worktree tree

**Worktree-mode artefact routing.** The plan's `<output>` block specifies `.planning/phases/01.11-search-analytics-dashboard/01.11-05-SUMMARY.md`, which lives OUTSIDE the git repo per the project's CLAUDE.md ("Keep Claude artifacts out of the repo"). ## Threat Flags

None. This plan operates entirely within the `<threat_model>` block written in `01.11-05-PLAN.md`:

- **T-01.11-05-01 (session-id tampering)** — mitigated by controller reading `HttpContext.Session.Id` server-side and never binding a `SessionId` form field on the view-model post path. Test `Submit_IgnoresClientSuppliedSessionIdField_UsesHttpContextSessionId` locks this at persistence level (row's `session_id` equals the server value, not the spoofed `"SPOOFED-SESSION-VALUE"`).
- **T-01.11-05-02 (XSS via WhatLookingFor / WhatGot / Email)** — mitigated by Razor auto-encoding on render (`@row.field`); textarea contents render as `@whatGotInitial` inside `<textarea>` so the HTML encoder fires; no `@Html.Raw` on any message field.
- **T-01.11-05-03 (DoS via huge payload)** — mitigated by `[StringLength(4000)]` on `WhatLookingFor` and `WhatGot`. The default Kestrel `MaxRequestBodySize` further caps the total payload.
- **T-01.11-05-04 (user leaves email in hide-checked state)** — mitigated by hint copy under the checkbox (`If you tick this box we will not store your email address, so we will not be able to reply.`) + the confirmation view showing the session id so the user can quote it later even without an email round-trip.
- **T-01.11-05-05 (repudiation)** — accepted per plan.
- **T-01.11-05-SC (package install)** — no new packages installed. Verified against `Directory.Packages.props`.
