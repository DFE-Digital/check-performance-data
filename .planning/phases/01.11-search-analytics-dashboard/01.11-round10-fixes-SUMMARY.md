# Phase 01.11 Round-10 Fixes: Seed Sample Search Data — Danger-Zone Delete

## One-liner

Adds an `is_seeded` boolean marker across the three sink tables and two destructive admin actions (Delete seeded / Delete all) on the Test data seed page, both behind GDS confirmation modals with the latter gated by a case-sensitive typed-confirmation input; every successful delete writes an AuditEntry.

## What shipped

**Schema layer**

- New EF migration `AddIsSeededMarker` adds `is_seeded BOOLEAN NOT NULL DEFAULT FALSE` to `search_events`, `search_event_results`, `search_messages`. No data backfill — existing rows default to `false` (real data).
- `SearchEvent`, `SearchEventResult`, `SearchMessage` entities each gain a `bool IsSeeded { get; set; }` property with matching snake_case column mapping in their configurations.
- `PortalDbContextModelSnapshot` regenerated by `dotnet ef migrations add` so the design-time model stays in sync.

**Write-side plumbing**

- `SearchEventDto` grew a trailing `bool IsSeeded = false` positional parameter — defaults preserve every existing call site's behaviour (real-events path unchanged).
- `DbSearchAnalyticsSink.RecordBatchAsync` reads `dto.IsSeeded` onto the parent `SearchEvent` row and mirrors the flag onto every child `SearchEventResult` row (parent + children stay in lockstep — a seeded parent never has non-seeded children).
- `SampleSearchDataSeeder` stamps `IsSeeded=true` on every event it builds; `DbSampleSearchDataGateway.WriteBackdatedMessagesAsync` stamps `IsSeeded=true` on every backdated message. Existing real-write paths (`SinkAndLogSearchTelemetry`, `DbSearchMessageService.CreateAsync`) are **not** modified, so real rows continue to default to `false`.

**Delete surface**

- `ISampleSearchDataGateway` grew two methods returning a new `DeleteCountsResult(EventsDeleted, ResultsDeleted, MessagesDeleted)`:
  - `DeleteSeededAsync` — `ExecuteDeleteAsync` with `WHERE IsSeeded` across the three DbSets, wrapped in `ExecuteInTransactionAsync`. Children deleted first so the returned counts are unambiguous.
  - `DeleteAllAsync` — same shape without the marker filter.
- `TestDataController` gained two new POST endpoints (`delete-seeded`, `delete-all`) under the existing `/admin/test-data/sample-search-data/` prefix. Both are `[ValidateAntiForgeryToken]`, both are dev-only (`IHostEnvironment.IsDevelopment()` → 404 in Test/Production), both write an `AuditEntry` on success with `Action = DeleteSeededSearchData` or `DeleteAllSearchData` and a payload carrying the per-table counts, `deletedBy`, `deletedAt`, `durationMs`. Delete-all additionally rejects with 400 unless the request supplies `confirm=DELETE` via form field or query string (case-sensitive Ordinal comparison).
- Both endpoints 302 back to the seed page with a `TempData` banner reading `"Deleted N events, M results, K messages from the sink."` — rendered through the existing GDS notification-banner block on the view.

**View**

- New Danger zone section on `Views/Admin/TestData/SampleSearchData.cshtml`, below the existing seed form:
  - `<hr>` section break + `<h2 id="danger-zone-heading">Danger zone</h2>` + `govuk-warning-text` banner.
  - Two `govuk-button--warning` submit forms — each opens a native `<dialog>` mirroring the existing seed-progress-modal shape.
- Delete-seeded modal: plain confirm (heading + body copy + primary/secondary buttons).
- Delete-all modal: heading + body copy + `govuk-input` labelled "Type DELETE to confirm" + primary button that starts disabled and enables only when the input value equals the literal `DELETE`.

**Client-side**

- New `wwwroot/js/test-data-delete.js`, wired into the view alongside the existing `test-data-seed.js`:
  - Intercepts the two submit-button clicks, opens the corresponding `<dialog>`.
  - Delete-seeded confirm button fetches POST with the anti-forgery token, reloads on success.
  - Delete-all: clears the input on every open, enables the primary button only on strict `value === 'DELETE'`, submits the typed literal in the `confirm` form field.
  - JS-less fallback: the delete-all form ships a pre-populated hidden `<input name="confirm" value="DELETE">` so a synchronous submit still passes the server-side guard.

**Tests**

- Integration (Postgres via Testcontainers, all pass — 21/21 across the three files):
  - `AddSearchAnalyticsMigrationTests` — `is_seeded` column presence on all three tables, default-false on insert without setting the flag.
  - `SampleSearchDataSeederTests.SeedAsync_MarksEveryRowAsSeeded` — invariants across seeder-run + a direct sink insert: seeded rows go up, real rows stay at 1, child result rows inherit the parent flag.
  - `SampleSearchDataDeleteTests` (new file) — DeleteSeeded preserves real, DeleteAll drops everything, empty-sink no-ops returning zero counts, per-table counts match what left the tables.
- E2E (Playwright, build-verified against the E2E project — live browser run deferred, see Deviations):
  - `DangerZone_ShowsBothDeleteButtons` — captures `test-data-danger-zone.png`.
  - `DeleteSeeded_WipesSeededRowsAndShowsBanner` — captures `delete-seeded-modal.png`.
  - `DeleteAll_ConfirmButtonRequiresTypedDelete` — captures `delete-all-modal-typed.png`.

## Deviations from Plan

### Rule 3 — fixed routing bug in the E2E screenshot helper

**Found during:** authoring the E2E test extension.
**Issue:** the existing `SaveScreenshotAsync` helper's if/else chain routed anything not matching `seed-in-progress-modal*` / `seed-completed-modal*` / `seed-cancelled-modal*` to `round8` — which would have landed all three new round-10 screenshots in the wrong folder.
**Fix:** added a third branch that routes `delete-*` and `test-data-danger-zone*` filenames to a new `danger-zone` subfolder.
**Files modified:** `tests/DfE.CheckPerformanceData.E2ETests/Admin/TestDataAdminTests.cs`.
**Commit:** commit 3 (E2E).

### E2E live-browser run deferred

**Reason:** the running `cypd_web` container is the shared harness for the parallel round-11 executor operating on `search-dashboard`. Rebuilding + restarting the container to apply the new migration would have disrupted their work. The E2E test suite is authored, compiles clean, and will run in CI on the merged branch. Integration coverage (Testcontainers-backed, isolated from the shared harness) validates the schema + gateway + typed-confirmation contract end-to-end without touching shared resources.
**Files:** none — this is a runtime deferral, not a code change.

### Style decision — reused native `<dialog>` shape rather than the Phase 02.2 `ConfirmModal` component

The Phase 02.2 `GovukConfirmModalTagHelper` was considered, but the seed page already carries the round-9 native `<dialog>` template + the `.seed-progress-modal` CSS class. Two dialogs of the same shape on the same page keeps the visual + CSS footprint zero. The `ConfirmModal` component would have introduced a second modal chrome pattern on the page for no functional gain.
