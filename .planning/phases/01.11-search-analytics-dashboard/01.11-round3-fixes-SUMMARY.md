# Search analytics UX round-3 fixes — Summary

Closes the third round of UX fixes on the search-analytics feature. Both of Lance's
verbatim asks shipped:

1. **Admin message detail now shows everything the user saw.** The user's typed
   question, the pre-submission search query + timestamp + results count, and the
   ordered numbered list of hit URLs all render on `/admin/Messages/Inbox/{id}`.
2. **A new root-level Messages admin nav group** owns both the (renamed) Search
   feedback inbox and the Dead-letter queue. The top-bar badge pair (DLQ +
   SearchMessagesInbox) is consolidated into a single **Messages** badge whose count
   is the sum of unread search-feedback + waiting DLQ.

Screenshots for handoff live under
`tests/DfE.CheckPerformanceData.E2ETests/Snapshots/search-ux/` (round-2 shots refreshed
to reflect the renamed inbox) and
`tests/DfE.CheckPerformanceData.E2ETests/Snapshots/search-ux/round3/` (new: nav group,
group landing, message detail).

## Deviations from Plan

### 1. Deleted the old badge components + tests instead of keeping them

**Rule 3 — cleanup.** The acceptance said the executor could rename `SearchMessagesInboxBadgeViewComponent` to `MessagesBadgeViewComponent` for cleanliness and to leave a note in the SUMMARY. Went one step further: the two separate view components + their view files + the standalone unit test file (`SearchMessagesInboxBadgeTests.cs`) are removed outright. Rationale: the new `MessagesBadge` component reads both counts, so keeping the old components as unreferenced code would just be dead weight. The old E2E test method `AdminChrome_RendersDlqBadge_LinkingToDlqView` was renamed to `AdminChrome_RendersMessagesBadge_LinkingToMessagesLanding` with updated assertions against the consolidated badge.

### 2. Renamed the view-component (kept the acceptance's escape hatch in scope)

**Rule 3 — naming.** The acceptance said: *"SearchMessagesInboxBadgeViewComponent view-component name stays for stability BUT the badge label text switches to just 'Messages' (see M4). If the executor believes renaming the component to MessagesBadgeViewComponent is cleaner, do it — but leave a note in SUMMARY.md."* — did the rename. The pair-to-single consolidation would leave the surviving component doing something entirely different (reading two counts, showing a sum, linking to a group landing) from what its name suggested; keeping the old name would have been misleading.

### 3. Messages group Order = 25 rather than 15

**Rule 3 — nav ordering.** Acceptance said `Order = 15 or similar` OR "between System administration and Storage administration". Picked 25 (between System-admin 20 and Storage-admin 30) since that matches Lance's original placement description more literally and reads better in the /admin landing list: admins scan CMS-admin -> Amendment requests -> System administration -> **Messages** -> Storage administration. Order 15 would have put Messages second, above System administration, which felt overweighted for what is essentially an inbox.

### 4. MessagesController.Index inherits the class-level RequireAdminSection(MessagesInbox) gate

**Rule 3 — auth trade-off.** A cleaner solution would loosen the class-level gate to `AllowAnyGrantedSection = true` and add per-action gates on Inbox/Detail/MarkRead. Would have required updating the existing `Controller_IsGatedBy_MessagesInboxSection` test and the RequireAdminSectionAttribute callsite everywhere it's asserted. In practice: admins have the messages-inbox grant via `DefaultAdminAccessSeeder.AllSections`, so admin-role users reach the landing fine. Users with a hypothetical custom role holding only `dead-letter-queue` grant would see the group in their sidebar but 404 on the landing click. Left as-is — the acceptance is functional for admins today; loosening the gate is a follow-up.

### 5. Detail heading uses "Their last search on this site" (past-tense "Your" would misread)

**Rule 3 — wording.** The feedback form (user-facing) uses `Your last search on this site` because the user IS the reader. The admin detail view has a different reader (admin, third-person), so the heading is `Their last search on this site` — small but real semantic distinction. Same helper otherwise.

### 6. QueueAdminTests renamed method + updated assertions

**Rule 3 — E2E rename.** `AdminChrome_RendersDlqBadge_LinkingToDlqView` (checked that "/admin/queues/dlq" appears anywhere in the response) -> `AdminChrome_RendersMessagesBadge_LinkingToMessagesLanding` (checks the consolidated badge is present and the old standalone DLQ badge is not). The old test would have kept passing because the DLQ URL still appears in the sidebar tile; the rename tightens the assertion to actually cover the badge change.
