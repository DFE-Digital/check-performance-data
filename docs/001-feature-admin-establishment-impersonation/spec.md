# Feature: Admin establishment impersonation

Approved specification (D-32). Open questions are resolved.

## Requirements

1. **R1 — Access:** Only a signed-in user holding both `cypmd_admin` and `cypmd_impersonation` can see the impersonation option or start impersonation (D-24). Both roles automatically grant access to this option without an additional admin-section grant, including access to its entry point on the admin landing page (D-31). Holding either role alone, an unrelated admin-section grant, or knowing the URL is insufficient. Other admin options retain their existing access rules.
2. **R2 — Entry:** The existing admin section provides an impersonation option leading to a form containing LAESTAB, URN, lowest age and highest age fields for manual entry. Both age fields require numeric whole-year values; missing or non-numeric ages show a field error and do not start impersonation. No external age verification or additional bounds/ordering validation is introduced in this version (D-27, D-29, proposed input handling D-30).
3. **R3 — Manual selection without identifier validation:** An authorised administrator manually enters LAESTAB and URN. This version uses those values without required-field, format, existence or establishment-match validation and performs no directory lookup before starting impersonation. Verification is deferred to a later increment (D-16). This does not bypass authentication, authorisation or protection of the selected context.
4. **R4 — Establishment context:** Successful selection makes establishment-scoped data pages use the selected LAESTAB and URN together, with checking-window eligibility derived from the manually configured age range (D-27). The administrator's user identifier and roles remain those supplied by their authenticated login; no establishment override can confer additional roles. The age range is stored with the same session-bound selection and cleared on exit.
5. **R5 — Visible mode:** Every application page rendered while impersonation is active displays a prominent red banner at the top with the text "Read-only impersonation", the selected LAESTAB and URN, and an explanation that changes cannot be saved or submitted. The mode remains clear without relying on colour alone.
6. **R6 — View data:** Existing views of the selected establishment's pupils, results and amendment requests, including existing draft amendments and data downloads, remain available wherever the normal establishment journey permits (D-23). Viewing a draft cannot edit it or submit it. Ordinary authentication and checking-window restrictions continue to apply; impersonation grants no additional access to closed windows.
7. **R7 — Read-only controls:** Controls that create, edit, save, delete, upload, withdraw, submit or otherwise change establishment data are visibly unavailable in impersonation mode. Data downloads, filtering and pagination remain available where they do not change business data.
8. **R8 — Server enforcement:** All business changes, including administrative changes, are blocked while impersonation is active. Direct or replayed change requests are rejected before any business change, file persistence, message enqueueing or external submission occurs, even when the UI is bypassed. The response explains that impersonation is read-only. Reviewed viewing actions, exit, sign-out and protective audit recording remain possible (D-17).
9. **R9 — Viewing requests:** A request that only navigates, searches, filters or downloads data is not blocked solely because it uses POST. Any exception to the read-only guard must be explicitly reviewed for side effects; unknown actions default to blocked while impersonating.
10. **R10 — Unauthorised overrides:** An ordinary user cannot switch establishments by changing query strings, form fields, cookies, headers or request bodies. Forged impersonation state or state belonging to another authenticated session cannot activate an override.
11. **R11 — Ongoing permission checks:** Each impersonated request requires the authenticated session still to hold both required roles. If either role is absent from the current authenticated principal, selected-establishment access is rejected and impersonation state is invalidated. Identity-provider role changes take effect under the existing login refresh behaviour unless a separate revocation mechanism is agreed.
12. **R12 — Protected selection:** Starting or changing impersonation requires an authenticated, authorised request with anti-forgery protection. Visiting a URL or receiving a cross-site request cannot silently change the selected establishment.
13. **R13 — Exit:** The red banner provides an "Exit impersonation" button. Using it clears the override and returns to the administrator's own context, where their usual admin sections and permitted actions become available again (D-18). Exiting in one tab ends impersonation for the whole authenticated session; subsequent requests in every tab cannot continue using the stopped impersonation state. Already rendered pages need not refresh automatically, but stale actions remain subject to R15 (D-19).
14. **R14 — Session lifecycle:** One establishment selection is bound to the authenticated session and shared across tabs using that session. Signing out or ending the authenticated session invalidates impersonation. A later sign-in does not restore a previous establishment selection. Separate authenticated sessions do not inherit each other's selection. Opening an ordinary new tab or window does not isolate impersonation; no incognito window is required or automatically opened. Impersonation cannot outlive its authenticated session (D-19); no additional impersonation-specific timeout is proposed in this version (D-20).
15. **R15 — No stale write context:** Starting, stopping or changing impersonation cannot carry draft or journey state from one establishment into another. A form loaded before a mode change must not write using a different establishment context when submitted afterwards.
16. **R16 — Consistent establishment details:** Pages identify the selected establishment by LAESTAB and URN rather than substituting the administrator's own establishment name or address. Checking-window eligibility uses the selected age range, not the administrator's own establishment eligibility (D-27). No target directory lookup is introduced. If another target-only detail is essential to a view and unavailable from this manual context or existing target data, that view remains unavailable with a clear explanation; original establishment metadata must never be substituted.
17. **R17 — Attribution:** Impersonation start, exit and blocked business-change attempts are recorded with the real administrator identifier, selected LAESTAB and URN, timestamp and outcome (D-21). Authentication credentials and session keys are never recorded. Support views must not be counted as genuine establishment logins or submissions. Individual data-view auditing and a mandatory support-reason field are not proposed for this first version (D-22).
18. **R18 — Ordinary journeys:** Users outside impersonation continue to use their login-supplied establishment and can perform their existing authorised actions. Development impersonation cannot enable the production feature or bypass its access checks.
19. **R19 — Hidden admin sections:** While impersonation is active, all admin navigation, sections, tiles and links are hidden. Direct requests to admin pages cannot render those sections while active; they explain that the administrator must exit impersonation first. The banner exit action and sign-out remain available. All administrative business changes are also blocked by R8 (D-17, D-18).
20. **R20 — Submission ownership safeguard:** Every business-write boundary rejects impersonation before writing. Outside impersonation, submission establishment identifiers are derived from the original authenticated login context, never from impersonation selection or browser-supplied identifiers. The request, pupil and journey being changed must belong to that authenticated establishment; mismatched or stale context is rejected before any write or external submission. This version uses the original authenticated claims and ownership checks, without a live identity-provider lookup per submission (D-26).
21. **R21 — Impersonation landing page:** Starting impersonation opens a landing page labelled with the selected LAESTAB and URN. Available checking windows must contain data for that LAESTAB and match the manually entered age range, while preserving existing checking-window dates and availability restrictions (D-27). If none qualify, display an empty-state explanation rather than falling back to the administrator's establishment. Use the numeric lowest and highest ages and the existing age-to-key-stage overlap rules: a key stage qualifies when the selected lowest age is less than its upper boundary and the selected highest age is greater than its lower boundary. Existing boundaries are KS2 3–11, KS4 14–16 and Post16 16–18 (D-29). These are the current eligibility boundaries, not new definitions of key-stage ages.

## Decisions

- **Confirmed scope:** Establishment-level viewing, with both admin and impersonation roles required, follows D-3, D-6, D-10 and D-11. The prominent red banner and manual LAESTAB/URN entry follow D-5 and D-7.
- **Viewing scope:** Allow viewing and downloads, including existing draft amendments wherever the normal establishment journey permits; no editing or submission (D-23).
- **Submission authority:** Use original authenticated establishment claims and ownership checks for writes; reject impersonation and stale target context without calling the auth server for each submission (D-26).
- **Manual identifiers:** Accept the manually configured LAESTAB and URN without identifier validation or a directory lookup in this version; verification is a future enhancement (D-16). Unknown or unusable identifiers must not fall back to another establishment's data.
- **Manual eligibility and landing page:** Add numeric lowest and highest age fields, show LAESTAB/URN in place of establishment name, and list checking windows with target data and matching eligibility using the existing organisation overlap rules (D-27, D-29).
- **Admin access while active:** Hide all admin sections and block all business changes until impersonation ends, with an exit button in the red banner (D-17, D-18). This avoids confusing the administrator's normal mode with the read-only establishment view.
- **Existing platform:** Retain the existing application and hosting platform; follows 000-project/D-1 and 000-project/D-6.
- **Role conjunction:** Require both `cypmd_admin` and `cypmd_impersonation` (D-24). Both roles automatically expose and authorise this admin option without an additional section grant (D-31); configurable section grants cannot enable impersonation for anyone missing either role (D-12). Preserve existing section-grant rules for other admin options.
- **Session binding:** Maintain one protected target selection per authenticated session, shared across its tabs and invalidated by exit, sign-out or session expiry (D-19). Preserve the authenticated identity; the proposed implementation leaves the identity-provider login ticket unchanged (D-13). This keeps the actor attributable and ordinary login claims authoritative.
- **Read-only enforcement (proposed):** Use a default-deny request guard with an explicitly reviewed set of viewing and impersonation-lifecycle actions, alongside unavailable UI controls (D-14). HTTP method alone cannot distinguish a view from a business change.
- **Existing context consumers:** CurrentUserService reads organisation identifiers, name, type and UKPRN from claims; LandingPageService also calls the sign-in organisation API. The spec must prevent mixed target and original organisation details (D-15).
- **Exit, lifecycle and audit:** The banner exit button is agreed (D-18), as is session binding (D-19). Audit start, exit and blocked change attempts with the real admin identity, target identifiers, timestamp and outcome (D-21). The existing authentication ticket is held in a protected distributed cache; the spec does not require changing that mechanism.

None.

## Review status

The draft follows the agreed intent and project principles; no contradictions were identified. The user has confirmed both-role access without an additional section grant, the manual establishment and age context, viewing scope, exit button, hidden admin sections, blocking all business changes, session binding, core audit events and original-login submission authority.

The user approved the complete spec and requested the implementation plan (D-32), including the unchanged login identity/ticket approach (D-13), default-deny guard with reviewed viewing exceptions (D-14), no additional impersonation timeout (D-20), no individual data-view audit or support-reason field (D-22), and minimal numeric age input handling (D-30). The route inventory during planning must verify that allowed views have no business-write side effects.

No earlier increment exists to supersede. No application code has changed. The project index is at spec while the implementation plan is under review.
